Follow-ups / Ranked improvement backlog (ranking axis: impact first, lower effort breaking ties):

1. **Build the dashboard tool** (the mission's explicit backlog proposal) — High impact, medium effort. What it would read: `fleet-status.json` across every directory under `.nelson/missions/`, plus `.active-*` markers. What it would surface: phase, last-updated age, and squadron/progress snapshot for every mission in one view — closing the exact gap that let the stale mission below sit unnoticed for three months. What it extends rather than replaces: `nelson-data.py status` already does this well for one mission; this is `status` generalized to "all missions," not a rewrite. Scope as its own mission — not built here, per sailing orders.
2. **Clean up the stale mission** — High impact, very low effort once decided. `.nelson/missions/2026-07-06_223339_761d8f37/` (outcome: external-repo-target support) is stuck at `BATTLE_PLAN`, never formed or stood down; `.nelson/.active-761d8f37` is still live. Needs a human call — resume it, or formally abort it (`scuttle-and-reform`) and remove the marker — not a captain's call to make unilaterally.
3. **Fix the `nelson-data.py event` / `nelson-phase.py` validator mismatch** — Medium-high impact, low-medium effort. Discovered firsthand this mission: `references/structured-data.md` documents `event --type task_completed --task-id N --owner ... --station-tier ... --verification ...`, but the installed `nelson-data.py`'s `event` subcommand only accepts `--type` and `--checkpoint` (confirmed via `--help`) and writes an empty `data: {}`. `nelson-phase.py`'s own `_check_underway_exit` requires `data.task_id` to count a task as complete. Net effect: following the documented CLI exactly cannot advance a mission from `UNDERWAY` to `STAND_DOWN` — this mission only got there because the admiral hand-edited `mission-log.json` directly to add the missing `task_id`. Either the `event` subcommand needs the typed per-event-type arguments the docs describe, or the docs need to drop them and say so plainly.
4. **Sync `fleet-status.json`'s cached outcome on sailing-orders amendment** — Low-medium impact, low effort. This mission's `sailing-orders.json` was amended (v1 → v2) by direct edit, since no `nelson-data.py` subcommand exists for amending sailing orders. `fleet-status.json.mission.outcome` still reads the original v1 text throughout the mission. Cosmetic — `sailing-orders.json` itself is the correct authority and both versions are intact there — but a quick `nelson-data.py status` read would show the wrong outcome. An `amend-sailing-orders` subcommand that updates both files together would close this.
5. **Recalibrate crew-sizing for research-heavy "atomic" documentation tasks** — Medium impact for future planning accuracy, low effort. Task 1 was correctly scoped as Station 0 / 0-crew / atomic per the standing orders, and that was the right call — but HMS Spey finished at 28% hull (Critical), having made 34 tool calls reading two full mission directories plus five repo docs for fidelity. "Atomic" and "zero crew" undersold how much real reading a trustworthy worked-example doc requires. Worth a note in `crew-roles.md`'s decision tree: a single clear deliverable that requires cross-referencing multiple real sources for accuracy can still be 0-crew, but should budget hull/context more like a research task than a single-pass fix.
6. **Task-list visibility tooling (`TaskCreate`/`TaskList`/`TaskGet`) is unavailable in this Claude Code build** — Low impact, effort unclear (environment-dependent). The skill's Step 4 instructions assume these tools exist for session-visibility tracking in every execution mode; this session's tool search came back empty. Mission proceeded without them (visibility-only, not coordination-blocking), but worth flagging since the skill's own instructions silently assume a capability not present here.
